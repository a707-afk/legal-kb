## 一句话定位

**一个能跑完"查法条 → 核时效 → 验引用"这条链路的法务审查 Agent。**

不是又一个"塞文档 → 向量检索 → 拼 prompt"的 RAG demo，也不是一个会聊天的问答机器人。
核心能力分两层：

### 第一层：Agent 控制循环的工程实现（基础能力）

带自纠正的控制循环 + 三层保护 + 全链路 trace：

```
Router（意图）→ 并行检索（向量 ∥ BM25）→ Grader（证据够不够？）
   → 不够 → 改写查询【重新检索】（不是重生成）→ 回到检索
   → 够 → Generator（受约束生成 + 条号引用）
   → Citation Verifier（条号能否命中？）→ 不能 → 带反馈重生成
   → 降级：迭代耗尽 → 输出"信息不足" + 已检索片段

三层保护：最大迭代 / 循环检测 / 异常回退
每一步落结构化 trace，可按 query_id 回放整条链路
```

> **实现状态（诚实版）**：Harness 已有 `plan → execute → evaluate → rewrite` 骨架 + 预算/超时/HITL + 权限门；
> 但上图的「改写 → **重新检索**」真闭环、Currency Check、Citation Verifier 仍是 **D5 待接**——
> 当前 rewrite 回环复用同批 observations、未重新检索（见 `docs/11-迁移终检报告.md` 第三节）。
> 设计已定、正在实现。

### 第二层：领域特有难度（差异化能力）

同一部法律在语料里有 2–4 个历史版本，系统必须判断哪一版现行有效、
哪一版已被修订、哪一版尚未生效，并在回答里说清依据。

> **为什么两层都要**：控制循环是任何 Agent 系统的基本盘，缺了它项目不成立；
> 但真正让这套系统区别于通用 RAG 的，是**法条时效治理**与**可程序判定的评测体系**——
> 通用 RAG 的做法在版本冲突题和位阶冲突题上会直接失败。

---

## 为什么是这个方向（三条，按硬度排序）

1. **可程序判定的版本 GT。** flk 官方元数据带 `status_code`（1=已废止 / 2=已被修订 /
   3=现行有效 / 4=尚未生效）与 `effective_date`，已实测：`status_code=4` 的 9 条全部满足
   "生效日期 > 今天"；360 个多版本标题里 353 个的 `status_code=3` 就是最新生效版。
   **"哪一版有效"不需要人工标注，是算出来的。**
2. **数据来源可信。** 国家法律法规数据库（flk.npc.gov.cn）官方 Word 原件，不是合成数据、
   不是爬来的网页。**数据从哪来、能不能复现，是这套系统可信度的前提。**
3. **闭环每一环都有确定性验证器。** 时效可查、引用可验——所以整个 Agent 闭环
   **可以自动判分**，不像"多 Agent 协作"那样没有 ground truth。

**技术栈**：Python 3.12 / FastAPI / Qdrant + BM25 混合检索 / RRF 融合 / bge-m3 嵌入 /
bge-reranker-v2-m3 重排 / 自研 Agent Harness / 智谱 `glm-4.5-flash` 生成。
**检索与嵌入全本地**（语料不出机器），生成层用云端免费档——这是 8GB 显存下的取舍，
不是省钱的妥协（见 `docs/06-环境与模型选型.md`）。

## 三个必须知道的事实

1. **旧评测数字一律不可引用。** 148 条评测集与语料同源（A 类金标=语料原文，D 类语料=金标并集），
   且 E2 与基线跑在不同版本上。
2. **旧项目的"法条时效治理"是空话。** 导入脚本读的字段名是 `status`，而官方元数据里叫
   `status_code` —— 一个字段名 bug 让 2,466 条全部落空，front-matter 的 `status` 硬编码成 `current`。
3. **案例库含真实姓名，且旧仓库是 public。** 本地已取的 500 篇里，约 403 个文件名是真实姓名
   而非"某某"脱敏形式。第一轮不纳入，且**不推送旧仓库**。见 `docs/04-风险与合规.md`。
