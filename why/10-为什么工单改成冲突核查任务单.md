# 10 工单 → 冲突核查任务单（Agent 的对外形态）

> 在 [00 全景图](00-系统怎么跑起来的.md) 的位置：主线三的 API 入口。
> 这篇讲**Agent 对外暴露成什么接口、为什么把一代的"工单"删掉换成"任务单"**。

## 1. 它在系统里是什么

- 现在只有一个 Agent 端点：`POST /agent/run`（`AgentRunRequest{objective, tenant_id, user_id, session_id, budget}`）
  → `run_agent_harness` → `AgentRunResponse`。
- **已删**：一代客服的 `POST /agent/ticket` + `TicketAgentRequest/Response`（带 `customer_id` / `customer_tier` / `ticket_note`）。

## 2. 为什么删（数据事实）

- 四个分库（法律/行政法规/司法解释/FAQ）里**一条业务工单数据都没有**。
- 旧项目的 `/agent/ticket` 端点"活着但无数据支撑"，还带 `customer_id`/`customer_tier` 这种电商客服字段——
  硬留着就是**没有数据的空壳**，评测零条、demo 靠假数据。

## 3. 代码怎么做的

- `src/api/routes_agent.py`：只保留 `/agent/run`（`AgentRunRequest`/`AgentRunResponse` 是本地 pydantic 模型）。
- `src/schemas.py`：删掉 `TicketAgentRequest`/`TicketAgentResponse`。
- `src/agent/harness.py::run_agent_harness`：`ticket_id` 仍作**中性可选引用字段**保留（不再是客服语义）。
- D-11 把"执行形态"重定义为**冲突核查任务单**：一个 Agentic 自纠正闭环
  （Router→Retriever→Currency Check→Grader→Generator→Citation Verifier→降级），3 个决策点都有确定性验证器。

## 4. 为什么必须这么造（工程约束）

- **"执行型"的价值不在"工单"这个壳，在闭环里的决策点**：多步决策 + 工具调用 + 中间判断，不绑定业务形态。
- **冲突核查任务单不依赖外部数据**：它的输入就是用户的法律问题，靠语料 + 时效/引用验证器闭环，
  所以能落地、能自动判分（工单状态机没有数据，做不到）。

## 5. 怎么验证它对

- `grep -rn "agent/ticket\|TicketAgent\|customer_id\|customer_tier" src/` 应为空。
- `POST /agent/run` 能跑通（`test_agent_harness.py` 的离线 run 测试覆盖了 harness 主体）。
- ⚠️ 现状（诚实）：冲突核查任务单的**闭环本体在 D5 落地**；现在 `/agent/run` 走通用 harness，
  改写回环还是"假的"（不重新检索，见 06）。

## 6. 代码位置
