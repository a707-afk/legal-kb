# 03 时效感知重排 currency（查询·精排后这一环）

> 在 [00 全景图](00-系统怎么跑起来的.md) 的位置：查询流程第 4 步 rerank **之后**、返回之前。
> 它是本项目区别于"通用 RAG"的核心逻辑——**让系统优先返回现行有效版**。

## 1. 它在系统里是什么

- **上游**：精排后的 top-k 片段（每个节点的 payload 带 `status_code` / `effective_date`）。
- **它做的**：按时效重新排序/过滤，输出最终 top-k。
- **下游**：`ScoredRetrieval` → API 响应 / 评测判分。
- **关键约束**：它是**独立、可单独开关**的一步（`currency_rerank_enabled`），
  这样才能做"开/关对照"，把"提升来自时效"从"来自检索/精排"里分离出来。

## 2. 两种模式（数据/接口）

```
apply_currency_rerank(nodes, query, settings, trace) -> nodes
```
- **默认模式**（查询无年份）：按 status_code 调分——
  `3 现行有效 +boost` / `2 已修订 −penalty` / `4 未生效 −penalty` / `1 已废止 −penalty`，再稳定重排。
- **时间旅行模式**（查询含年份，如"2020 年时"）：`extract_year_anchor` 抽出年份 →
  同一法名只保留 `effective_date ≤ 该年末` 的最新一版。

## 3. 代码怎么做的（`src/currency.py`）

- `extract_year_anchor(query)`：正则 `(?:19|20)\d{2}(?=\s*年)` 抽时间锚点。
- `apply_currency_rerank()`：关（默认）就原样返回；开则按上面两模式处理，并 `trace.record("currency", ...)`。
- `_time_travel_filter()`：按 `title` 分组，每组取 `effective_date ≤ cutoff` 里最新的一版。
- 权重都在 config：`currency_current_boost` / `currency_superseded_penalty` / `currency_pending_penalty` / `currency_repealed_penalty`。
- 接入点在 `src/retrieval.py`：精排（或 `merged[:top_k]`）之后统一调一次，再构造 `ScoredRetrieval`。

## 4. 为什么必须这么造（工程约束）

- **必须独立可开关**：如果塞进 rerank 的打分里，就分不清"排序变好"是时效的功劳还是精排的功劳，
  D4 的"开/关对照 + 过期法条率"无从归因（这正是 why/03 旧版反复强调的点）。
- **默认关**：让"纯语义检索"成为干净基线；时效重排的净收益 = 开 − 关，可量化。
- **只读 payload 的 status_code/effective_date**：不重新检索、不改召回，是纯重排层，副作用可控。

## 5. 怎么验证它对

- `python scripts/run_eval.py --both`：跑 baseline（关）vs currency（开），对照每类 accuracy + **过期法条率**
  （top-1 的 status_code≠3 占比）。期望：D 类（版本冲突）accuracy 上升、过期法条率下降。
- 单元验证：构造"旧版分数略高 + 新版 status_code=3"的候选，开启后新版应被提到前面。

## 6. 代码位置

- `src/currency.py`（`extract_year_anchor` / `apply_currency_rerank` / `_time_travel_filter`）
- `src/retrieval.py`（精排后的接入点）
- `src/config_LEGACY_REFERENCE.py`（`currency_*` 开关与权重）
- `scripts/run_eval.py`（`--both` 出对照 + 过期法条率）；正式账本 `BLUEPRINT.md` D-06
