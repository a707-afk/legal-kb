## 系统只有两条主线：建库（离线）+ 查询（在线）

### 主线一：建库流程（离线，一次性）

入口：`scripts/ingest_npc.py`（导入）→ `scripts/build_index.py`（建索引）

```
官网 docx 原件 + metadata.jsonl（含 status_code / effective_date / 版本号 bbbs）
   │
   │  ingest_npc.py：读 docx 正文，套上官方时效元数据，渲染成带 front-matter 的 .md
   │                 （每部法的每个历史版本 = 一个独立 .md，文件名 = {标题}_{bbbs}.md）
   ▼
data/docs/{statute, interpretation, faq}/*.md        ← 2951 篇
   │
   │  build_index.py：
   │   [1] load_documents → build_nodes（chunking.py：**按"条"切**，每节点带 heading_path=编/章/节/条）
   │   [2] duplicate_check（全文 MD5 自检，"同位置重复"必须 = 0）
   │   [3] embeddings.py：bge-m3 把每个节点编成 **1024 维**向量（结果缓存在 data/.embed_cache）
   │   [4] 向量写入 Qdrant 集合 legal_kb_m3 + persist_bm25_corpus 生成 BM25 语料
   ▼
Qdrant（server 模式, :18333）: legal_kb_m3 = 88681 个点，每点 payload 带 status_code / effective_date / heading_path…
BM25: data/bm25_corpus.jsonl
```

**关键**：时效元数据（status_code 等）在 [1] 就随节点进了 payload，一路带到检索结果里——
这是"能判断哪一版现行有效"的数据基础（详见 01、02、11）。

### 主线二：查询流程（在线，每次问答）

入口：`src/api/routes_rag.py`（`/retrieve` 只检索、`/chat` 检索+生成）→ 核心在 `src/retrieval.py`

```
用户问题
   │  InputGuard（input_sanitizer.py）：拦 prompt 注入 / 越权检索
   ▼
retrieve_scored_nodes（retrieval.py）
   │  0. 查进程内缓存（cache.py）——命中直接返回（热查询 0ms）
   │  1. query_rewrite.py：把口语问题改写成更适合检索的句子
   │  2. 两路**并行**（带 20s 超时预算，某路超时就降级用另一路，绝不挂死）：
   │       ├─ 向量路：问题编成向量 → Qdrant HNSW 近邻 → top-N
   │       └─ BM25 路：bm25_store.py 关键词匹配 → top-N
   │  3. 融合：RRF 或 max（_merge_hybrid_by_*）把两路合成一个候选集
   │  4. rerank：bge-reranker-v2-m3 对候选精排（rerank.py）
   │  5. gate：gates.py，最高分低于阈值就判"拒答"
   │  ※ 全程 trace.py 逐 stage 落一条 JSONL，事后可 replay_trace.py 回放整条链路
   ▼
ScoredRetrieval（top-k 片段，每片带 status_code / heading_path 等）
   │
   │  只有 /chat 才继续：拼 prompt → llm.py 调 SenseNova 生成答案
   │                     → citation.py + legal_refs.py 做**条号级引用校验** + 句级 grounding
   ▼
答案 + 引用块 + grounding 报告
```

### 主线三：Agent 流程（在线，多步任务）

入口：`src/api/routes_agent.py`（`/agent/run`）→ `src/agent/harness.py`

```
objective（任务目标）
   ▼
run_agent_harness：
   风险评估(_assess_risk) → 注入检测 → 意图分类 → 规划(_build_plan：LLM 或规则兜底)
   → 逐步执行：每个工具调用都经 tool_registry 的
        [参数校验 → 权限门(permission_gate) → 幂等检查 → 执行]，失败走三分类+退避重试(D-13)
   → 生成草稿 → OutputGuard 脱敏 → 评估(_evaluate_result) → 改写回环 → HITL 判定
   → 结果落 JSONL（src/db，一个 run 一个文件）
   工具只有两个：local_search（调上面的检索主线）+ synthesize（调 LLM 综合证据）
```

## 组件地图（谁负责什么、代码在哪）

| 环节 | 模块 | 一句话职责 |
|---|---|---|
| 导入 | `scripts/ingest_npc.py` | docx + 官方元数据 → 带时效 front-matter 的 .md |
| 切块 | `src/chunking.py` | .md → 按"条"的节点，带 heading_path（见 11）|
| 向量 | `src/embeddings.py` | 文本 → bge-m3 1024 维（本地快照、零网络，见 12 附）|
| 向量库 | `src/vector_store.py` | 节点 ↔ Qdrant；建库 / 加载 / **维度断言** |
| 关键词 | `src/bm25_store.py` | BM25 语料持久化 + 检索 |
| 检索编排 | `src/retrieval.py` | 两路并行 → 融合 → 重排 → 门控（系统心脏）|
| 重排 | `src/rerank.py` / `qwen_rerank.py` | bge-reranker 精排 |
| 门控 | `src/gates.py` | 分数不够 → 拒答 |
| 时效重排 | `currency`（**D4/D5 待建**）| 按 status_code 加权/过滤（见 03）|
| 引用校验 | `src/citation.py` / `legal_refs.py` | 条号级校验 + 句级 grounding（见 09）|
| Agent | `src/agent/harness.py` 等 | 规划-执行-评估-回环（见 06）|
| 可观测 | `src/trace.py` / `telemetry.py` / `logging_utils.py` | 链路 trace + 回放（见 08）|
| 缓存 | `src/cache.py` | 进程内检索结果 LRU（见 14）|
| 持久化 | `src/db/` | AgentRun/Step 的 JSONL 落盘（见 07）|
| 配置 | `src/config_LEGACY_REFERENCE.py` | 所有开关/阈值，`get_settings()` 读 `.env` |

## "时效"到底体现在哪（本项目的灵魂，单独讲）

每个节点的 Qdrant payload 都带 `status_code`：`3=现行有效 / 2=已被修订 / 1=已废止 / 4=尚未生效`。
检索召回后，top-k 里同一部法的不同版本**各带自己的 status_code**——
"系统返回的是不是现行有效版"就靠这个字段判：D 类评测题、以及将来的 currency 重排，都读它。
这就是为什么"保留全部版本 + 每条带 status_code"是整个项目的地基（01、02）。

## 怎么亲眼看到它跑起来

```bash
# 建库（离线，需 Docker 起 Qdrant + 本地 bge-m3）
docker compose up -d qdrant
HF_HUB_OFFLINE=1 python scripts/build_index.py

# 检索冒烟 + 看链路
python scripts/smoke_retrieval.py --query "公司拖欠工资能解除劳动合同吗"
python scripts/replay_trace.py --last        # 回放刚才那条查询的每一 stage

# 评测集
python scripts/build_eval_set.py --dry-run    # 看六类各能生成多少题
```
