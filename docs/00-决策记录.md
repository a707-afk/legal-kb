## D-14 只复制不移动，旧仓库完整保留

- **日期**：2026-09-28
- **背景**：需求是把有用资产迁移到新目录，避免旧项目越改越乱。迁移方式未指定。
- **备选**：(a) 移动（旧仓库清空）(b) 复制后清理旧仓库 (c) **只复制，旧仓库原样保留**
- **选择**：**(c)**
- **代价**：磁盘多占约 660 MB + 旧仓库的 134 MB `.git`；短期内两处并存可能混淆
- **理由**：迁移本身是一次高风险的取舍（判错就丢资产）。保留旧仓库 = 任何判错都可回滚。
  且旧仓库有 11 个未推送 commit，删除等于不可恢复。
- **量化**：新目录 660 MB；旧仓库 `.git` 134 MB
- **设计评审要点**：
  - L1「为什么不直接删旧的？」→ 判错的成本不可逆；保留的成本只是磁盘
  - L2「两处并存会不会又乱？」→ 旧仓库冻结为只读历史，新项目只在 `legal-kb`（本仓库）演进；
    边界写进 `docs/05-迁移清单.md`
  - L3「什么时候可以删旧的？」→ 新项目跑通完整评测（D4）之后

## D-17 权限做、观测换形态、多租户只做隔离语义（部分推翻 D-16）

- **日期**：2026-09-28
- **背景**：用户表示"确实希望有多租户、权限、可观测性"，要求研究本项目是否需要。
  D-16 曾把多租户 / 可观测性整体删掉。
- **备选**：(a) 全部恢复（含 OPA + Prometheus）(b) 维持全删 (c) **按"是否解决真问题"逐个重判**
- **选择**：**(c)**
- **代价**：新增约 1.7 天工作量（隔离语义 2h + 检索 trace 半天 + Agentic 闭环 1 天）
- **结论**（详见 `08-工程能力取舍.md`）：
  | 能力 | 结论 | 形态 |
  |---|---|---|
  | 多租户 | 不做完整版 | payload 字段 + 检索前 pre-filter（2h） |
  | 权限 | **做** | 工具权限门（已迁移）+ 数据 pre-filter |
  | 可观测性 | **做，但换形态** | **检索链路 trace + 回放脚本，不做 Prometheus** |
  | Agentic 闭环 | **做（重点）** | Router→Retriever→Currency→Grader→Generator→Verifier |
- **依据**：
  1. 多租户在没有多客户时是伪需求；系统真正需要的是故障可定位、可复现（稳定性 / 故障根因分析）
  2. 权限的 pre-filter vs post-filter 有一代实测：**42% → 88.5%（+46.5pp）**
  3. Prometheus 对 RAG 的四种失败模式（没召回 / 排序错 / 用错片段 / 引用错条号）**全部看不见**
  4. 一代自己的 `MARKET-REALITY.md` 写明标杆项目是 **Agentic RAG 自纠正闭环**，但一代没做
- **设计评审要点**：
  - L1「为什么不做多租户？」→ 个人项目没有多客户，真正的需求是数据隔离。但**保留隔离语义**，
    因为 pre-filter vs post-filter 有 46.5pp 的实测差距，这是个真技术点
  - L2「为什么可观测性不做 Prometheus？」→ Prometheus 能看延迟和错误率，但 RAG 的失败是
    "召回了但排在第 8 名"这种，指标上完全看不出来。需要的是链路 trace
  - L3「为什么重点补 Agentic 闭环？」→ 系统的价值在"LLM 是决策者"，不是固定 Pipeline。
    而且本项目的闭环每一环都有**确定性验证器**（时效可查、引用可验），能自动判分

## D-18 生成层改用智谱免费档 `glm-4.5-flash`（推翻 D-10 的"纯本地"）

- **日期**：2026-09-28
- **背景**：用户提出"云端模型删不掉，如果要就用智谱免费的最强模型试试"，并提供了 key。
- **备选**：(a) 纯本地 Ollama（需新装 + 拉 2.5–5GB 模型 + 8GB 显存紧张）
  (b) 智谱免费档 (c) 两者都做，本地为主云端为对照
- **选择**：**(b) 为主**，本地列为 P2
- **代价**：引入外部 API 依赖；"数据不出内网"的叙事需要修正为"**检索与嵌入全本地，生成可选云端**"
- **量化（实测，2026-09-28）**：

  | 模型 | 延迟 | 引用质量 |
  |---|---|---|
  | `glm-4.5-flash` | 33.8s | ✅ 条号精确到"第（二）项"，格式规范 |
  | `glm-4-flash` | 1.0s | ❌ 只给"《劳动合同法》第三十八条、第四十六条"，无推理 |

  账户**余额为 0** → 只能用免费档 → **零财务风险**。

- **理由**：引用精度是本项目核心指标（D-07 条号级校验），1s 的 `glm-4-flash` 达不到要求。
  33.8s 延迟对法律问答可接受（210 题评测约 2 小时）。
- **设计评审要点**：
  - L1「为什么不用本地 LLM？」→ 8GB 显存要同时放 bge-m3(2.3G) + reranker(2.3G)，
    只剩 3.4G，只能上 4B-Q4，质量不如 `glm-4.5-flash`。**且需要新装 Ollama。**
  - L2「那"数据不出内网"这个性质怎么办？」→ 修正口径：**检索与嵌入全本地（语料不出机器），
    生成层可选云端**。这仍然是合理的架构——法律知识库的敏感数据是"用户的查询意图"，
    而不是公开法条本身
  - L3「如果要求全本地呢？」→ 降级预案：`qwen3:4b` + 分时加载（检索时载 reranker，
    生成时卸载）。质量会降，但链路完整

## D-20 定位改为"法务审查 Agent"，闭环与 MCP 提到关键路径

- **日期**：2026-09-28
- **背景**：定位需要从"时效感知检索"上移到"能跑完一条任务链的系统"。原设计的 11 条决策
  全部围绕"检索与评测"，**0 条围绕"Agent 控制循环的工程实现"**——重心偏了，据此重新核定。
- **核实结果**（工程依据）：
  - RAG 是这类系统的基础能力，但只有 RAG 会停在"检索项目"
  - Agent 控制循环的构成要素：Function Calling / MCP、多 Agent/编排、Eval/可观测性、安全治理——
    缺一项链路不成立
  - 36氪《2026 中国 AI Agent 行业发展研究报告》（2026-09-27）：Agent 与对话式 AI 的分界是
    "**信息响应 vs 任务执行与结果交付**"；行业垂直类 Agent 明确包含"**法务审查**"
  - KPMG 2026Q2：53% 企业部署 Agent，但**跨工作流多 Agent 编排只占 18%**（说明多 Agent 非默认最优）
- **备选**：(a) 维持"时效感知检索"定位 (b) 改成通用"法律 RAG" (c) **改成"法务审查 Agent"**
- **选择**：**(c)**
- **代价**：闭环 + MCP 约 1.5 天新增到关键路径；原 D5 对照实验被挤到收尾期
- **关键判断**：**RAG 没有被 Agent 取代，而是成了 Agent 的必备子能力。**
  所以本项目"法律 RAG + 时效治理"不是白做，是**必备的那一半**；缺的是另一半（闭环 + MCP + Eval）。
- **设计评审要点**：
  - L1「为什么要改定位？」→ 系统的判据是"能不能跑完任务"而不是"答得准不准"。
    只做检索的项目会停在"信息响应"那一侧
  - L2「RAG 不是过时了吗？」→ 恰恰相反，它是必备子能力。过时的不是 RAG，
    是"只有 RAG"
  - L3「那要不要补多 Agent？」→ **不补实体**。KPMG 数据 18% + 36氪"并非天然优于单 Agent"。
    用"边界判断"说明设计取舍，比硬做一个没有 GT 的多 Agent 强

### D-23.1 63 个 OLE2 `.doc` → 用本机 Word COM 一次性转 docx

- **背景**：`data/raw/npc/*/files/` 里有 63 个文件是真正的 Word 97-2003 二进制格式

- **备选**：(a) 跳过这 63 篇 (b) 自研 OLE2 + FIB/分片表解析器 (c) **用本机已装的 Word 做 COM 批量转换**
- **选择**：**(c)**
- **代价**：依赖本机 Word（`C:\Program Files\Microsoft Office\...\WINWORD.EXE`）与 `pywin32`；
  转换产物需重新生成一次（`data/raw/` 已 gitignore）。1 个文件的产物缺 `officeDocument` 关系，
  `python-docx` 会拒开 → 已加 `word/document.xml` 直接解析的回退路径。

- **设计评审要点**：
  - L1「为什么不跳过？」→ 会以"文件缺失"的名义静默丢掉 58 篇司法解释，

  - L2「为什么不自研解析器？」→ OLE2 + Word 分片表（clx/piece table）解析成本远高于收益，

  - L3「可复现吗？」→ 是。`scripts/convert_doc_to_docx.py` 幂等（已存在则跳过），

### D-23.2 输出文件名用**完整 bbbs**，且冲突即抛错

- **背景**：旧脚本用 `{title}_{version[:8]}` 作文件名。实测 `bbbs` 是

  - L3「为什么旧脚本没炸？」→ 旧脚本"同名只保留最新"，标题已去重，

### D-23.3 目录（TOC）剥离判据：首个目录条目的**最后一次出现** + 后随实质内容

- **背景**：官方 docx 的正文前有"目录"块，会把章/节名列一遍。不剥离会污染检索
  （同名章节重复出现，互相竞争 top-k）。

- **选择**：**(d)**

  - (b) 失败：司法解释的目录里含 `一般规定`、`调查`、`提起诉讼` 这类

- **设计评审要点**：
  - L1「怎么判断剥离对了？」→ 判据不是"看起来干净"，而是

  - L2「假设正文不重复首章标题怎么办？」→ 有回退：目录块退化为"短行连续段"，

## D-26 切块改为**条级最小单元**（`chunk_split_on_tiao=true`）

- **日期**：2026-09-28
- **背景**：`hierarchical_recursive` 原先只按 markdown 标题（编/章/节）切块。
  但 `BLUEPRINT.md` §1.2 明确写的是"**法条按'条'为最小单元**，保留 `heading_path` = 编/章/节/条"

### D-26 附：重复自检口径修正

原验收"重复节点 = 0"按**纯文本**判重，实测有 1,538（标题级）/ 10,956（条级）个"重复"。
逐条复核后确认**其中 99.99% 是合法现象**，判据本身错了：

|---|---|---|

### D-31 D4 加严判据 + 修 rerank 爆炸：版本冲突题 0.40→0.85

- **日期**：2026-09-29
- **背景**：D-30 首跑 D 类准确率饱和在 1.0——judge 太松（“期望版本在 top-k”，多版本近似重复几乎必中），区分不出 baseline/currency。用户又指出 F 类“语料外应快速拒答”要查。
- **诊断（用 trace，不猜）**：replay 一道卡 110s 的题 → **rerank 单步 109s**。根因：`_rerank_cross_encoder` 调 `CrossEncoder.predict()` **没传 max_length**，bge-reranker-v2-m3 默认按模型上限 **8192** 处理，长候选触发 O(n²) 注意力爆炸。（之前误判为“F 类语料外慢/BM25 慢”——实测语料外热态仅 917ms、BM25 仅 3ms，真凶是 rerank。）
- **修复**：
  1. `rerank_max_length=512`（config）传给 `predict(pairs, max_length=512)`——法条节点很短，512 足够判相关。**单题 rerank 109s→~1s，8 题冒烟 187s→21s，全量 40min 跑不完→~5min**。
  2. 早退 gate（`retrieval_early_gate_*`）：向量 top-1 余弦 < 阈值时跳过 rerank。**阈值实测校准**：初设 0.30 一次未触发（bge-m3 对语料外也给到 0.45–0.50 余弦，下不到 0.30）；实测同域命中 min=0.588、语料外 min=0.386，定 **0.45**（验证：天气0.499不早退/快排0.448早退/拖欠工资0.742不早退，零误拒）。**结论**：向量余弦是弱信号，早退 gate 只能抓最极端的语料外、且仅是省 rerank 的锦上添花；**真正的拒答靠 rerank 后的 cross-encoder 门控**（区分度更高，F 拒答 13/15），“快速”靠的是 rerank max_length 修复（109s→1s）。
  3. 加严 judge：`version_effective_at_year`→**top-1==期望版本**；`detect_not_effective`→**top-3**。
  4. 修一个自引入的 bug：`row.update(top1_status=…, **info)` 与 judge info 的 `top1_status`/`top1` 键碰撞 → TypeError → 30 道 D 题被误 skip（改名 info 键修复）。
- **加严后的硬数字（195/210，A–E 全、F 半）**：

  | 指标 | baseline | currency | Δ |
  |---|---|---|---|
  | **D 版本冲突** | **0.40 (16/40)** | **0.85 (34/40)** | **+0.45** |
  | E 位阶/未生效 | 0.75 | 0.55 | **−0.20** |
  | **过期法条率(top1)** | **31.5%** | **5.3%** | **−26.2pp** |
  | overall | 0.672 | 0.744 | +0.072 |
  | A/B/C/F | 0.72/0.85/0.5/0.87 | 同 | 0 |

- **怎么解读**：
  - 加严后 **D 类终于能区分**：baseline 0.40（时间旅行题几乎全错——返回现行版而非当时版），currency 0.85（时间旅行过滤 + 现行版加权生效）。
  - **E 类反而掉 0.20**：currency 无差别给 status_code=4（未生效）降权，而 E-未生效题问的正是未生效版 → 被挤出 top-3。**这是“一刀切降权”的真实缺陷**，直接指向 D5 的意图感知 currency（问“生效了吗”时不该降权未生效版）。
  - A/B/C 不变：它们判“来源在不在 top-k”，currency 只在 top-k 内重排。
- **教训**：① 判据太松会让指标饱和、掩盖真实差异——评测的价值在“能区分”不在“好看”。② 慢要用 trace 定位到 stage，别凭直觉归因（我一开始也猜错了 F/BM25）。③ 可观测性（逐题 latency + trace）是把 109s 这种爆炸措出来的前提。
- **产物**：`reports/eval_both_report.json`、`eval_rows.jsonl`（含逐题 latency_ms/best_vector_score/early_gate）。
