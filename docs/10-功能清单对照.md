## 二、Agent 核心机制清单（"Agent 架构核心组件"的具体所指）

"Planning / Memory / Tools / Action 怎么落地的"，指的就是这四项：

| 机制 | 本项目实现 | 状态 | 缺口 |
|---|---|---|---|
| **Planning（规划）** | `_build_plan`（LLM）+ `_build_plan_rule_based`（兜底）+ `sub_questions` 拆解 | ✅ | 规划质量无评测 |
| **Memory（记忆）** | `ResearchAgentState` 存 trace / facts / sources；`session_id` 绑多轮 | 🟡 | **无跨会话长期记忆**；无上下文压缩 |
| **Tools（工具）** | `tool_registry`（副作用/风险/幂等/校验）+ `permission_gate` | ✅ | 工具数量少（2 个）；无 MCP |
| **Action / Reflection（执行与反思）** | 工具执行 + `_evaluate_result` 自评 + **rewrite 回环** + 预算封顶 | 🟡 | 自评是 **LLM 判断**，缺确定性判据 |

**关键洞察**：四个机制**都有实现**，问题在于**它们都没有被单独评测过**。
这正好指向第 7 条（Eval）——**评测体系不只是"补一个模块"，而是让上面四项从"写了"变成"验证过"。**

## 五、一句话对照

| | 市场要的 | 你有的 | 你要补的 |
|---|---|---|---|
| **检索** | RAG 100% | ✅ 超配（+ 时效治理） | 无 |
| **工具** | Function Calling / MCP 86% | ✅ 注册表 + 权限门 | **MCP** |
| **编排** | 流程编排 67% | ✅ Harness 骨架（含 rewrite 回环） | 领域验证器 |
| **评测** | Eval 67% | 🟡 设计有，runner 缺 | **runner + trace** |
| **多 Agent** | 67% | ➖ 不做 | **用 18% 数据回答"为什么不做"** |
| **记忆** | Memory 系统 | 🟡 会话级有 | 跨会话记忆（P2） |
| **安全** | 48% + 治理要求 | ✅ 权限门 + pre-filter 调用点 | 接上实现（已补迁） |

> **最值钱的一句**：你的项目**不缺模块，缺的是"这些模块被验证过"的证据**。
> 评测体系（runner + trace + 六类题）就是把"写了"变成"验证过"的那道工序——
> 而它恰好是行业高频要求、当前又普遍空白的那一项。
