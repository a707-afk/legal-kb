# 05 迁移清单

> 生成方式：`scripts/migrate_from_legacy.py`（幂等，支持 `--dry-run` / `--audit`）
> 机器可读版本：`reports/migration-manifest.json`
> **版本 v2（2026-09-28）** —— v1 有三处漏、一处位置错，v2 已修正。修正记录见第七节。
> 源仓库：旧仓库 `a707-afk/REACTAGENT`（**public**）

## 零、迁移原则

1. **只复制，不移动、不删除。** 旧仓库完整保留，可随时 diff / 回滚。
2. **按"是否解决过真问题"取舍**，不按"代码好不好看"取舍。
3. **闭包完整**：迁进来的模块，其依赖必须一起迁（或明确标为"待重写"），
   否则就是"迁了模块但 import 全断"的**假迁移**。
4. **迁移必须包含测试。** 只迁实现不迁测试 = 把"已验证"变成"未验证"。
5. 原始数据全量迁（含全部历史版本），因为路线 A（法条版本冲突）需要它们。

### 7.3 教训（可复用）

迁移审计不能只看"目标目录里有没有东西"，必须做**双向核对**：

1. **从源仓库的完整文件清单反查**：有没有该迁未迁的（→ 发现 tests/ 与环境文件全漏）
2. **从新项目的 import 图反查**：有没有断链（→ 发现 7 个依赖模块漏迁）
3. **从迁入文件的内部内容反查**：有没有指向已删模块的残留（→ 发现 docker-compose 与 CI 里的死引用）

只做单向（看"我迁了什么"）必然同时漏掉**依赖**和**测试**，而且会把旧包袱一起带进来。

## 八、复现方式

```bash
python scripts/migrate_from_legacy.py --dry-run   # 预演
python scripts/migrate_from_legacy.py --audit     # 只审计完整性
```

脚本幂等，可安全重复执行。执行后读 `reports/migration-manifest.json` 核对。
