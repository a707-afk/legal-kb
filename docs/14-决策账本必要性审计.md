# 14 决策账本必要性审计

> 触发：逐条复核决策账本的必要性——没必要的不要硬加，
> 每条都要能对应当前的工程约束。
> 时间：2026-09-28 ｜ 方法：**每条挂工程依据，无依据的砍掉或合并**

## 第零章 先修正定位

判断标准：项目的核心不是"只做法律行业"，而是**做一个足够深、选题足够通用的工程系统**，
这样它的适用范围不被单一领域锁死。

**对。此前把"法务"写成了行业定位，等于把项目适用范围从一个通用工程能力缩到"法律科技"一格。**
法律科技产品恰恰要求法律背景 + 3–5 年经验，是最窄的一格。

### 修正后的定位

| 项 | 修正前 | **修正后** |
|---|---|---|
| 定位 | 垂直行业：法务 | **Agentic RAG 工程能力（不限行业）** |
| 语料的角色 | 行业标签 | **只是语料选择**——因为它的 GT 可程序判定 |
| 适用范围 | 法律科技（要求法律背景 + 3–5 年） | **所有做 Agent / 知识库的系统** |

**定位说明相应改为**："我用法律语料做这个项目，因为它的正确答案可以程序判定
（法条版本由官方元数据决定）——**这是为了能自动评测，不是为了做法律行业**。"

## 第一章 审计方法

对 `BLUEPRINT.md` 的 17 条决策逐条问三个问题：

1. **工程依据**：不做这条会怎样？对应什么实际约束？（技能频次统计 + 外部调研 + 36氪报告）
2. **不写会怎样**：这一环会不会成为设计盲点、评审时答不上来？
3. **是不是硬凑**：如果删掉，项目会缺什么？

**原则**：没有工程依据的 → 删；能合并的 → 合并；是"技术动作"而非"决策"的 → 降为附录。

## 第四章 旧设计文档的吸收边界

旧设计文档（`PROJECT-1-AGENTIC-RAG.md`）内容庞杂，**需要区分"吸收什么"和"不吸收什么"：**

| 那份文档有什么 | 处置 |
|---|---|
| ✅ **结构**：五层评估指标 / 5 类坏例归因 / 三层保护 / Grader 阈值标定法 / 设计评审要点 | **吸收**——这些正好补 D-08 / D-12 / D-14 |
| ❌ **技术栈**：LangGraph、React、Langfuse + Prometheus、三级缓存 | **不吸收**——蓝图明确不做多 Agent 实体；Prometheus 对 RAG 归因无用 |
| ❌ **内容**：一代客服的数字（41 篇 / 50 题 / RRF +4 / Agent 15/15） | **不吸收**——换成本项目数据 |
| ❌ **工时估算**：120–150 小时 | **不吸收**——那是按另一个规模的项目估的，与本项目规模不匹配 |

**所以 D0 的任务不是"搬那份文档"，是"取它的结构，换掉它的内容和栈"。**

## 第五章 结论

1. **定位修正**：不限行业，语料只是语料
2. **决策账本从 17 条收敛到 14 条**，删掉 3 条无工程依据的（其中 2 条是我上一轮硬凑的）
3. **补了 2 条真缺口**（Context Engineering、MCP），它们有 67% / 86% 的工程依据
4. **每条决策都挂了工程依据**——没有依据的不进账本
5. `PROJECT-1-AGENTIC-RAG.md` 只取结构，不取内容与技术栈
