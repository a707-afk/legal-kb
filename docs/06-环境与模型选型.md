### 2.3 bge-m3 —— **损坏，必须重修** ❌

**诊断结论**：`resolve_local_hf_snapshot('BAAI/bge-m3')` 返回 `None` 的**真因不是"不识别 m3 缓存布局"**

有人手动把两个 snapshot 拼凑在了一起：一个放配置、一个放权重。

> ### ⚠️ 2026-09-28 D2 复测：**上述"缓存损坏、必须重下"的判断是错的**
>
> 实测 `refs/main` 指向的 snapshot 里**有 `pytorch_model.bin`（2.27 GB）**，
> 而 sentence-transformers 完全可以从 `pytorch_model.bin` 加载——**不缺任何东西**。
> 之前的诊断只查了 `model.safetensors` 一个文件名就下了"权重缺失"的结论，
> 属于**"截断输出当证据"**（HANDOFF §9.4 的同款错误：只看了文件名列表的一部分）。
>
> 实测（`HF_HUB_OFFLINE=1`，纯本地零网络）：

> 编码成功 维度: 1024  前3值: [-0.0171, 0.0615, -0.0267]

>
> **结论：不需要重下 2.3 GB。** 下表三个方案均**不再需要**，保留仅作故障排查参考。
> 另注：`snapshots/9a0624b8.../` 只有 `model.safetensors` 没有配置，是**孤儿目录**，
> 不影响加载（resolver 优先走 `refs/main`）。

## 三、显存预算（8 GB 是硬约束）

| 组件 | 精度 | 估算占用 |
|---|---|---|
| bge-m3（568M 参数） | fp16 | ~2.3 GB |
| bge-reranker-v2-m3（568M） | fp16 | ~2.3 GB |
| 小计（检索链路常驻） | | **~4.6 GB** |
| 剩余给 LLM | | **~3.4 GB** |

**LLM 可选方案**：

| 模型 | 量化 | 占用 | 可行性 |
|---|---|---|---|
| Qwen3-4B | Q4_K_M | ~2.5 GB | ✅ 可常驻（4.6 + 2.5 = 7.1 GB） |
| Qwen3-8B | Q4_K_M | ~5.0 GB | ⚠️ 需分时加载（检索完卸载 reranker） |
| Qwen3-8B | Q8 | ~8.5 GB | ❌ 不可行 |

**三级预案**：
1. 上 Qwen3-4B-Q4 常驻（最简）
2. 8B + 分时加载：检索阶段载 reranker，生成阶段卸载 reranker 载 LLM
3. reranker 移到 CPU（延迟 +1~3s，但可用）

**待实测**：三模型共存的真实显存占用与首 token 延迟 → 回填到 `BLUEPRINT.md` D-10。

## 四、LLM 选型：SenseNova（商汤）`sensenova-6.8-flash-lite`（**2026-09-28 定案**）

> **本节已于 D2 重测并改写。** 原结论"主模型 glm-4.5-flash（智谱）"**已废弃**，
> 原因是**样本量为 1 的延迟测量不可信**——见 4.3 的对照数据。
> 决策记录见 `docs/00-决策记录.md` **D-24**。

### 4.1 定案

| 项 | 值 |
|---|---|
| 后端 | **SenseNova（商汤）**，唯一后端 |
| 模型 | **`sensenova-6.8-flash-lite`** |
| API | `https://token.sensenova.cn/v1/chat/completions`（OpenAI 兼容） |
| 凭据 | `SENSENOVA_API_KEYS`（**复数**，逗号分隔多 key 自动轮转） |
| reasoning | 独立字段 `reasoning_content`（**不混进 content**），`completion_tokens_details.reasoning_tokens` 可见 |
| 限流 | `LLM_MAX_RPM=10`（滑窗）+ 最小间隔 1.0s + 指数退避带抖动 |

**为什么统一到单一后端**：双后端意味着同一份评测可能跑在不同模型上 → **指标不可比**。
这正是旧项目"E2 与基线跑在不同版本上"那类事故的翻版。`LLM_BACKEND` 只接受 `sensenova`，
设成别的值**直接报错**（不静默回退）。

### 4.2 可用性探测（2026-09-28）

| 模型 | 可用 | 备注 |
|---|---|---|
| `sensenova-6.8-flash-lite` | ✅ | **定案主模型**；条号可精确到"第（二）项" |
| `deepseek-v4-flash` | ✅ | 备选；更快但给出项号的题数更少 |
| `glm-4.5-flash` | ✅（已弃用） | 免费档，但延迟高（见 4.3） |
| `glm-4-flash` | ✅（已弃用） | 免费档，延迟仍高 |
| `glm-4.6-flash` | ❌ | `1220 您无权访问` |
| `glm-4.5` / `glm-4.5-air` | ❌ | `1113 余额不足` |

### 4.3 可复跑对照（`scripts/bench_llm_backends.py`，6 题 × 受约束合成任务）

> **⚠️ 这是本节最重要的一条修正**：原文档记录的
> "`glm-4.5-flash` 33.8s / `glm-4-flash` **1.0s**"是**单次测量**。
> 样本量提到 6 题后，`glm-4-flash` 的 p50 是 **19.4s**，不是 1.0s——
> **单样本延迟不可作决策依据**（首次请求的缓存/冷启动会让数字严重失真）。

| 模型 | 延迟 p50 | 条号精度 | 给出项号的题数 |
|---|---|---|---|
| `glm-4.5-flash` | **32.5s** | 1.0 | 0/6 |
| `glm-4-flash` | **19.4s** | 1.0 | 0/6 |
| **`sensenova-6.8-flash-lite`** | **5.1s** | **1.0** | **2/6** |
| `deepseek-v4-flash` | **3.7s** | **1.0** | 1/6 |

**选型结论**：`sensenova-6.8-flash-lite`——条号精度 1.0，给出项号的题数最多（对 D-07
条号级校验最有利），延迟只有 glm-4.5-flash 的 **1/6**。

**对评测预算的影响**：210 题 × 5.1s ≈ **18 分钟**（原按 33.8s 估算是约 2 小时）。
若计入 D5 闭环的多次迭代（改写重检 + 带反馈重生成），按 3 倍估约 1 小时。

### 4.4 判分口径的一个坑（**已修，且 D-07 必须注意**）

首轮对照把 `sensenova-6.8-flash-lite` 的条号精度算成 **0.781**，
原因是模型写 `第577条`（阿拉伯数字）而语料原文是 `第五百七十七条`（中文数字），
朴素正则把**正确引用判成了幻觉**。

修法：`src/legal_refs.py` 提供 `cn2arabic` / `normalize_article_text`，
比较前**两侧都归一化**。同一问题在 D-07 的条号级引用校验里会导致**大量误杀**，
所以该模块是 D-06/D-07 的地基，不是可选项。

### 4.5 凭据规则

> 🔑 key **只从环境变量读**（`SENSENOVA_API_KEYS`），`.env` 已 gitignore 且**不放真实 key**，
> `.env.example` 只放占位符。多个 key 逗号分隔，遇 429 会自动换下一个并拉长限流间隔。
> 已在对话中出现过的 key 属**已暴露状态**，建议用完到控制台轮换重建。

## 七、已知的环境级副作用（迁移自旧项目）

| 项 | 说明 |
|---|---|
| `sitecustomize.py` WMI 补丁 | 旧项目为绕开 `platform._wmi_query` 永久挂起而打的**全局补丁**，影响本机所有 Python 进程（含其他项目）。**新项目不迁移**，改为在启动脚本里局部处理 |
| `HF_ENDPOINT=https://hf-mirror.com` | 本机直连 huggingface.co 被阻断，必须走镜像 |
| `NO_PROXY=localhost,127.0.0.1` | 本机有代理会劫持 localhost 请求（曾导致 Qdrant 502）。**现已在代码里强制**：`src/__init__._apply_local_no_proxy()` 包导入时写回 `os.environ`（`.env` 的值只进 Settings，httpx/qdrant-client 读不到），见 D-30 |
| Qdrant 端口 | 旧项目用 **18333**（16333 落在 Windows 保留端口段）。新项目沿用 18333 |
