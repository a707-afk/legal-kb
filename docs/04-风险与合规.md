# 04 风险与合规

> 这个项目的核心价值是"法律合规"。**所以它自己的合规问题必须先解决**——否则这套系统自身的合规问题就会成为它的短板。

---

## 一、个人信息（PII）—— **最高优先级**

### 1.1 事实

| 项 | 实测 |
|---|---|
| 案例库文件数 | 500（LeCaRD 刑事判决书） |
| **含真实姓名的文件** | **约 403 个（80.6%）** |
| 脱敏形式（某某/某甲） | 约 97 个 |
| 样例 | `107顾林欣危险驾驶罪一案`、`58陈凯交通肇事罪一案`、`丁宁、高文武盗窃、诈骗一案`、`侯振东、周永光等与冯延武非法采矿罪一案` |
| 目标仓库 | `a707-afk/REACTAGENT`，经 GitHub API 核实 **`private: false`（public）** |
| 当前推送状态 | **11 个 commit 未推送 → 风险尚未发生** |

### 1.2 为什么这是真风险

- 文书本身来自中国裁判文书网（公开），但 **2021 年后最高法已要求公开文书脱敏**；LeCaRD 是 2020 年数据
- 把 500 份含真实姓名的刑事判决书**二次发布**到公开仓库，是新的公开行为
- 更尖锐的是：**一个叫"法律合规知识库"的项目，自己带着个人信息合规问题**

### 1.3 处置（三选一，推送前必须做）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 案例库不进 git：在 `.gitignore` 中排除 `data/docs/legal/case/` 与 `data/raw/lecard/candidates/`，只保留生成脚本 | 零成本；仓库里没有判决书原文 |
| B | 批量重命名文件名为 `case_<idx>.md`，正文当事人姓名替换为"某" | 需写脱敏脚本；正文改写有语义风险 |
| C | 不纳入案例库 | 放弃类案检索能力（第一轮评测本来也不用它） |

**建议 A + 第一轮评测不使用案例库**（它同时还有"金标在库内"的评测失真问题，见 `02-评测设计.md`）。

## 三、免责与边界

### 3.1 标准答法

> "我做的是**检索与引用工程**，不是法律咨询。系统的责任是**给对出处**，不是判断你的案子能不能赢。
> 法条对错有官方原文可查，所以我把'引用可验证'做成了硬约束——答案里的每个条号都必须能在
> 检索片段里命中，否则系统拒绝输出。"

### 3.2 系统必须能拒绝的三类问题

| 问题类型 | 正确行为 |
|---|---|
| "我这个案子能赢吗" | 拒答 + 说明系统边界 |
| "帮我起草合同/协议" | 拒答 + 说明只做检索 |
| 语料外领域（如涉外法律、税务筹划） | 拒答 + 说明语料范围 |

**拒答能力本身就是能力**，不是缺陷——它证明系统知道自己不知道什么。

## 五、还没被任何人提到、但会影响项目的六件事

> 这一节是本次审查中**未在旧蓝图、旧日志、旧分析文档里出现**的问题。

### 5.1 "工单"是空壳

题材写"法律合规知识库问答 **+ 工单**"，README 写"工单状态机"，`/agent/ticket` 端点在代码里活着
（harness + local_search + synthesize）—— 但四分库里**没有一条工单数据**，工单评测**零条**。

而"任务形态差异化（问答 → 执行）"是《选题差异化》里效果评级"高"的杠杆，也是一代 Harness 的强项。
**这是唯一能把项目从"检索型"升级到"执行型"的抓手，现在是空的。**

→ 处置见 `BLUEPRINT.md` D-11（建议改为"冲突核查任务单"，不依赖业务工单数据）。

### 5.2 "幻觉治理"这个最强理由，一行都没验证

选法律题材的理由之一是"幻觉治理故事最锋利"。但旧基线是**纯检索**，生成层当时跑不通，
`citation_verify.py` 从未被评测。**引用溯源与幻觉校验是生成层能力，旧评测体系完全不覆盖。**

→ 新项目把引用校验（条号级）列为 D-07 必做项，并进评测指标（引用准确率）。

### 5.3 领域适配性分析

本项目的定位不是"法律行业项目"，而是**一个带领域特有难度的检索与 Agent 工程实践**。
选法律语料的原因不是行业偏好，而是它的正确答案可由官方元数据程序判定
（法条版本由 `status_code` 决定）——**这让"自动评测"成为可能**；
否则整条链路的效果只能靠人工打分，无法做回归验证。

这个定位必须写进项目文档：它决定了本项目的价值在于**工程方法与可评测性**，
而不在于对法律业务的覆盖深度（那是另一个问题，本项目不做）。

### 5.4 时间账与"两个项目"的冲突

- 9/26 结论：**不做第二个项目**
- 9/27 备选项目分析：**用户定案做两个**（项目二 = 财报勾稽，10 月中旬开工 2–3 周）
- 而项目一的法律方向在 9/28 才刚回到起点（语料要重建、评测要重做）

**两个项目 + 5 天窗口 = 不可能。** 建议：项目一按 `PLAN.md` 跑到 10/2，
**项目二的决定推迟到 10 月中旬**——届时看项目一的实际进度再定，不要现在锁死。

### 5.5 位阶关系是简化模型

本项目的"位阶"是从 `source_category`（法律 / 行政法规 / 司法解释）推导的**简化版**。
真实的法律位阶还包括宪法、地方性法规、部门规章、自治条例等，且**同一位阶内的新旧冲突、
特别法优于一般法、上位法优于下位法**等规则本项目都没有实现。

→ 边界必须在文档中写明：**本系统实现的是三类来源的位阶排序，不是完整的法律适用规则引擎。**
把边界说在前面，比被问出来强。

### 5.6 案例库的评测失真尚未解决

即使脱敏，"用金标挑选语料"这个循环仍然存在（`case_include.json` 先入池再补足）。
旧项目实测：20 条查询的 151 个金标文件**全部在库、缺失 0 条** → 答案键就在语料里。

→ 如果将来要恢复类案检索，必须**先随机抽样语料，再在语料内找可用金标**，顺序反过来。
