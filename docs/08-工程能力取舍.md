# 08 工程能力取舍：多租户 / 权限 / 可观测性

> 问题来源：多租户、权限、可观测性这三项要不要做，取决于本项目是否真的需要它们。
> 本文件用三个标准逐个判断，给出**做 / 不做 / 做什么形态**的结论。

---

## 一、判断标准（三条，缺一不可）

| # | 标准 | 说明 |
|---|---|---|
| 1 | **市场是否需要** | 行业需求里有没有；没有就是自嗨 |
| 2 | **项目是否有对应的真问题** | 不是"技术上能不能做"，是"这个系统真的会因此坏掉吗" |
| 3 | **成本是否可承受** | 在 5 天窗口内；超过半天的要打折 |

**关键区分**：同一个词在"企业 SaaS"和"个人项目"里指的完全不是一回事。
"多租户"在企业里是组织架构 + 计费 + 数据隔离；在个人项目里**只剩数据隔离**。
**按市场真实要求做形态，不按词面做功能。**

---

## 二、多租户：**不做完整版，只做"隔离语义"**

### 判断

| 标准 | 结论 |
|---|---|
| 市场是否需要 | ❌ **不需要**。行业能力要求（`07-一代实验结论.md` §7.1）没有一条要求多租户 |
| 项目是否有真问题 | ❌ 没有。语料是公开法规，没有租户归属；个人项目没有多个客户 |
| 成本 | 完整版 1–2 天（租户模型 + 隔离 + 测试） |

### 结论：**不做租户管理，但保留隔离语义**

具体做法（成本 **2 小时**）：

1. 文档 front-matter 与 Qdrant payload 保留 `tenant_id` / `audience` / `security_level` 三个字段
   （旧 `ingest_legal_corpus.py` 本来就在写这三个字段，成本为零）
2. 检索时支持**检索前 pre-filter**（而不是检索后过滤）
3. 不做：租户注册 / 组织管理 / 成员权限 / 计费

### 为什么保留"隔离语义"而不是彻底删掉

因为 **pre-filter vs post-filter 是一个有真实技术含量的问题**，而且一代已经做过实验：

| 口径 | Expect top1 |
|---|---|
| 仅 Post-filter | 11/26 (**42%**) |
| Pre-filter + 归一化 + Rerank | 23/26 (**88.5%**) |

**+46.5pp 的差距。** 这是"我做过实测、有数字"的结论，而不是"我觉得应该前置过滤"。
成本 2 小时换一个有 46.5pp 实测支撑的技术点，性价比极高。

---

## 三、权限：**需要，且已迁移**

### 判断

| 标准 | 结论 |
|---|---|
| 市场是否需要 | ✅ 需要，但形态是"**工具权限 + 数据访问控制**"，不是 RBAC 系统 |
| 项目是否有真问题 | ✅ **有**。Agent 会调用工具（`local_search` / `synthesize` / 时效核查），**工具必须有权限** |
| 成本 | 已迁移 `src/agent/permission_gate.py`，≈0 |

### 结论：**保留，两个层面**

1. **工具权限门**（已迁移）：Harness 调用工具前校验，防止 Agent 越权
2. **数据访问 pre-filter**（见第二节）：检索前过滤候选集

**为什么这对 Agent 项目是真问题**：一代的能力要求分析里明确要求"Agent 工作流设计、工具调用集成"。
而"工具权限"是 Agent 工程的核心话题之一——**Agent 会自己决定调什么工具，所以权限必须在工具层强制，
不能靠 prompt 约束**。这是一个能展开讲的判断。

---

## 四、可观测性：**需要，但形态完全不同**

### 判断

| 标准 | 结论 |
|---|---|
| 市场是否需要 | ✅ 需要，但措辞是"**故障排查经验**""**稳定性问题**""**故障根因分析**"（行业要求都提了） |
| 项目是否有真问题 | ✅ **有，而且是本项目最大的短板** |
| 成本 | 正确形态 半天；错误形态（Prometheus）1–2 天且无收益 |

### 关键区分：Prometheus 指标 ≠ RAG 的可观测性

一代做的是 `app/metrics.py` + `observability.py`（Prometheus `/metrics` + HTTP/检索延迟 + OTel）。
**这是通用后端可观测性，对 RAG 的失败归因几乎没用。**

RAG 系统的失败有四种，而且**从指标上看不出来**：

| 失败模式 | Prometheus 能看到吗 |
|---|---|
| 检索没召回（候选集里就没有正确答案） | ❌ 只看到延迟正常 |
| 召回了但排序错（正确答案在第 8 名） | ❌ |
| 召回了、排序也对，但生成时用错片段 | ❌ |
| 引用错了条号（答案说第 38 条，内容其实是第 46 条） | ❌ |

**这正是旧项目最大的问题**：`EVAL.md` 里**没有失败归因章节**，
所以 148 条评测跑完只知道"分数是多少"，不知道"为什么错"。
（本次审查靠重跑原始结果才补出归因：A 类 14 条漏检中 13 条是真未召回、1 条是口径误伤。）

### 结论：做**检索链路 trace**，不做 Prometheus

具体做法（成本 **半天**）：

```
每次查询落一条结构化 trace（JSONL）：
{
  "query_id": "...",
  "query": "...",
  "steps": [
    {"stage": "intent",    "result": "statute_exact", "ms": 3},
    {"stage": "vector",    "top": [{"node_id":..., "score":..., "file":..., "status_code":3}, ...], "ms": 12},
    {"stage": "bm25",      "top": [...], "ms": 8},
    {"stage": "fusion",    "method": "rrf", "top": [...], "ms": 1},
    {"stage": "currency",  "boosted": [...], "filtered": [...], "ms": 1},
    {"stage": "rerank",    "top": [...], "ms": 640},
    {"stage": "gate",      "passed": true, "max_score": 0.72, "threshold": 0.55}
  ],
  "answer": "...",
  "citations": [{"law": "...", "tiao": "第三十八条", "verified": true}]
}
```

配套一个**回放脚本**：`python scripts/replay_trace.py <query_id>` → 打印完整链路。

**为什么这个比 Prometheus 值钱**：
1. 它是**失败归因的前提**——没有 trace，评测只能告诉你"错了多少"，不能告诉你"错在哪一步"
2. 它是**可现场验证的**——问"你怎么定位问题"，可以当场回放一条 trace
3. 它直接对应行业要求里的"故障排查经验""故障根因分析"

## 五、这三个之外，真正该补的是另一个东西

对照 `07-一代实验结论.md` §7.3，**一代自己写下的"标杆项目"是 Agentic RAG 自纠正闭环**：

```
Router → Retriever → Grader（召回够不够？不够就改写重检）
       → Generator → Hallucination Checker（无支撑就带反馈重生成）
终止条件：最大迭代 / 上下文充分 / 降级
```

**而一代实际做的是"检索 + 评测"，Harness 有工具调用但没有 Grader 闭环。**

行业要求明确提到"Agent 工作流设计、工具调用集成、记忆管理"，
`MARKET-REALITY.md` 也写着"这不是 Pipeline，是真正的 Agent——LLM 是决策者"。

### 结论：把 D-11 的"冲突核查任务单"做成这个闭环

本项目的版本（不需要业务工单数据）：

```
用户问题
  → Router：判断意图（法条精确 / 口语咨询 / 版本询问 / 跨法条 / 无答案）
  → Retriever：向量 + BM25 + 融合
  → Currency Check：候选的时效状态是否与问题意图匹配？
        若不匹配（问现行却召回旧版）→ 带"时效约束"改写查询重检
  → Grader：召回的证据够不够回答？
        不够 → 改写查询重检（最多 2 次）
  → Generator：受约束生成 + 条号引用
  → Citation Verifier：条号是否都能在片段中命中？
        不能 → 带反馈重生成（最多 1 次）
  → 降级：迭代耗尽则输出"信息不足"并给出已检索到的片段
```

**这个闭环的每一环都有确定性验证器**（时效可查、引用可验），所以可以自动判分——
不像"多 Agent 协作"那种没有 GT 的设计。

## 六、最终清单

| 能力 | 结论 | 形态 | 成本 | 依据 |
|---|---|---|---|---|
| 多租户 | **不做完整版** | payload 字段 + 检索前 pre-filter | 2 小时 | 行业无要求；但 pre-filter 有 42%→88.5% 实测 |
| 权限 | **做** | 工具权限门（已迁移）+ 数据 pre-filter | ≈0 | Agent 项目真问题；行业要求工具调用 |
| 可观测性 | **做，但换形态** | 检索链路 trace + 回放脚本（**不做 Prometheus**） | 半天 | 行业要求"故障排查/根因分析"；Prometheus 对 RAG 失败归因无用 |
| **Agentic 闭环** | **做**（这才是重点） | Router→Retriever→Currency→Grader→Generator→Verifier + 降级 | 1 天 | 一代自己写的标杆；行业要求明确 |
| OPA 策略引擎 | **不做** | — | — | 个人项目伪需求 |
| Prometheus / OTel | **不做** | — | — | 通用后端指标，对 RAG 归因无用 |
| Redis 缓存 | **降级 P2** | 进程内 LRU 起步 | — | 单机项目 |

**合计新增成本约 1.7 天**，换来三个可量化、可演示、对应行业需求的能力。

> **取舍原则重申**：判断一个功能要不要做，问的是"**不做会暴露什么工程缺陷**"，
> 而不是"它看起来先不先进"。多租户看起来先进，但补不上任何真实缺陷；
> 检索 trace 看起来很土，但能回答"你怎么定位问题"。
